# Dashboard Touch wire protocol — version 1

Normative. Both the firmware and the helper implement this document, not
each other. Shared test vectors live in `docs/protocol-vectors.json`,
generated by `helper/tools/gen_vectors.py`.

## Transport

USB CDC serial, 115200. Line-oriented ASCII, `\n` terminated. Binary
fields are lowercase hex. The host must assert DTR or the ESP32-S3's
native CDC stays silent.

## Pairing

A 32-byte pairing key, generated at setup. Host copy: macOS Keychain,
service `DashboardTouch-pairing`, account = board serial. Device copy:
`PAIRING_KEY` in `secrets.h` (gitignored).

## Device → host lines

| Line | Meaning |
| --- | --- |
| `BOOT dashtouch <fw> proto=1` | printed once at reset; host resets its replay counter to 0 |
| `READY` | sensor handshake passed |
| `ERR sensor_unreachable` | sensor handshake failed at boot |
| `EV <nonce> <counter> <slot> <score> <hmac>` | fingerprint match event |
| `TYPED` | password typed and wiped |
| `ERR helper_timeout` | no valid `PW` within 3000 ms of `EV` |
| `ERR bad_response` | `PW` present but failed to decrypt/authenticate |
| `PONG`, `STATUS_OK ...`, `ENROLL_*`, `DELETE_*` | replies to host commands |

`EV` fields: `nonce` = 32 hex chars (16 random bytes, fresh per event);
`counter` = decimal uint32, strictly increasing from 1 within a boot;
`slot`, `score` = decimal from the sensor's Search result;
`hmac` = 64 hex chars.

**HMAC construction:** `hmac = HMAC-SHA256(pairing_key, ascii(canonical))`
where `canonical` is the exact line content before the hmac field:
`EV <nonce> <counter> <slot> <score>` (single spaces, no trailing space).

## Host → device lines

| Line | Meaning |
| --- | --- |
| `PING` → `PONG` | link check |
| `STATUS` → `STATUS_OK proto=1 fw=<fw> sensor=<ok\|fail> cap=<n> paused=<0\|1>` | versions + sensor state |
| `ENROLL <slot>` | start enrollment; device walks `ENROLL_WAIT_FINGER_1` → `ENROLL_REMOVE_FINGER` → `ENROLL_WAIT_FINGER_2` → `ENROLL_OK <slot>` / `ENROLL_FAIL <stage>` |
| `DELETE <slot>` → `DELETE_OK <slot>` / `DELETE_FAIL <slot>` | remove a template |
| `PW <gcmnonce> <ct>` | the one-time encrypted password answering the pending `EV` |
| `SETTINGS` → `SETTINGS_OK idle_color=<0-7> idle_style=<1-2> press_enter=<0\|1> fp_swap=<0\|1>` | read the stored device settings |
| `SET idle_color <0-7>` → `SET_OK idle_color <n>` / `SET_FAIL idle_color` | set the idle ring color (0 = off/dark) and persist to NVS; applies immediately if currently idle |
| `SET idle_style <1-2>` → `SET_OK idle_style <n>` / `SET_FAIL idle_style` | set the idle ring style (1 = steady, 2 = breathing) and persist to NVS; applies immediately if currently idle |
| `SET press_enter <0\|1>` → `SET_OK press_enter <n>` | set whether Return is pressed after typing the password, and persist to NVS |
| `SET fp_swap <0\|1>` → `SET_OK fp_swap <n>` | set the sensor UART's TX/RX pin orientation (0 = config.h's pins as declared, 1 = swapped) and persist to NVS; re-initializes the sensor UART and re-runs the handshake immediately, no reboot needed |
| `SET <unknown key> ...` → `SET_FAIL <key>` | unrecognized settings key |
| `PAUSE <0\|1>` → `PAUSE_OK <n>` / `PAUSE_FAIL` | pause (1) or resume (0) match scanning; transient session state, never persisted to NVS |

Plaintext commands carry no secrets and trigger nothing a person at the
device couldn't do by touching it.

## Pause

`PAUSE 1` stops the main loop's match scan entirely — no `GenImg` poll, no
ring change to reading, no `EV` — until `PAUSE 0` or the auto-resume below.
It does not touch enrollment or deletion; `ENROLL`/`DELETE` run normally
while paused. Pause state is transient (RAM only, never written to NVS): a
reboot always comes up unpaused, so a device can't get stuck deaf across a
power cycle.

**Auto-resume:** if no `PAUSE 1` refresh arrives within 90 seconds of the
last one, the firmware clears the pause on its own. This is the safety net,
not the mechanism — the web page is expected to refresh well inside that
window (every 30s) for as long as a naming/renaming field stays open, and
to send `PAUSE 0` itself on save/cancel/close. The 90s timeout only matters
when the page can't get a message through at all (crashed helper, closed
tab, dropped connection).

## Response encryption

On a valid `EV`, the host answers within 3000 ms:

1. `response_key = HMAC-SHA256(pairing_key, "DTPW1" || nonce_bytes)` (32 bytes; `"DTPW1"` is 5 ASCII bytes, `nonce_bytes` the 16 raw nonce bytes).
2. `gcmnonce` = 12 fresh random bytes, hex-encoded in the line.
3. `ct` = AES-256-GCM(response_key, gcmnonce, plaintext=UTF-8 password, aad=none), transmitted as ciphertext||tag (tag = final 16 bytes), hex-encoded.

The device derives the same key, decrypts in RAM, types, wipes. A `PW`
line is valid only for the most recent `EV` (its nonce) and only once.

## Replay rules (host side)

Track `last_counter`, starting at 0, reset to 0 on `BOOT` or a new serial
session. Accept an `EV` only if its counter is strictly greater; then set
`last_counter` to it. Reject everything with a bad HMAC before looking at
anything else.

## Out of scope

The sensor↔MCU UART is unauthenticated (inherent to R503-class parts).
Flash access without eFuse hardening exposes the pairing key. Both are
treated in `security.md`.

## Test vectors

`docs/protocol-vectors.json` pins: the EV canonical string and its HMAC
for a fixed key/nonce/counter/slot/score, the derived response key, and a
full `PW` line for a fixed GCM nonce and password. Any implementation must
reproduce all of them byte-for-byte.
